# Audit Skema Database — 23 September 2026

Seluruh riwayat migration kini **utuh, `001`–`035`, tanpa celah**, dan terverifikasi sinkron antara repository dan database.

**Masalah yang dibereskan.** Perubahan skema Sprint 011 (Edit Profile dan Notification Preferences) dulu dijalankan langsung lewat Supabase SQL Editor dan tidak pernah tercatat sebagai migration maupun di-commit — database tidak bisa dibangun ulang dari nol. Seluruh objeknya ditarik ulang dari struktur database hidup menjadi migration `022`–`026`, ditulis idempotent, lalu diterapkan dengan `supabase db push`.

**Tiga temuan selama audit:**

1. **`public.profile_completeness_rules` punya RLS aktif tanpa satu pun policy.** Query langsung dari client di `EditProfileForm.tsx` selalu mengembalikan nol baris — daftar field wajib diam-diam kosong. Gejalanya menipu: progress bar tetap tampak benar karena dihitung RPC `check_profile_completeness()` yang `SECURITY DEFINER` sehingga menembus RLS. Diperbaiki di `025`, terverifikasi policy-nya kini ada.

2. **Tabel `customer.*` punya policy RLS tapi tanpa GRANT sama sekali.** Policy `authenticated_all` sudah benar, tapi role `authenticated` tidak pernah diberi hak akses dasar — query ditolak Postgres sebelum RLS sempat dievaluasi. Ini akan memblokir modul CRM dan integrasi lead intake. Diperbaiki di `027`.

3. **Hak tulis berlebih pada tabel referensi di schema `public`.** Supabase memberi GRANT ALL ke `anon` dan `authenticated` secara default, sehingga tabel wilayah dan `profile_completeness_rules` ikut membawa hak INSERT, UPDATE, DELETE, bahkan TRUNCATE yang tidak pernah diniatkan. Dicabut di `027`, disisakan SELECT untuk `authenticated` saja.

**Empat temuan lanjutan dari database linter Supabase** (`028`–`030`):

4. **`check_profile_completeness` bisa dipanggil tanpa login.** Fungsi `SECURITY DEFINER` ini terbuka untuk role `anon`, sehingga siapa pun tanpa akun bisa menanyakan kelengkapan profil user mana pun lewat REST. Ditutup di `028`.

5. **`search_path` empat fungsi `core` tidak dikunci**, termasuk `is_authenticated()` yang dipakai policy RLS di seluruh tabel domain. Dikunci di `028`, dan diverifikasi fungsinya tetap berjalan sehingga RLS tidak lumpuh.

6. **Mengunci EXECUTE ternyata butuh dua pencabutan.** Postgres memberi EXECUTE ke `PUBLIC` saat `CREATE FUNCTION`, sementara Supabase menambahkan grant eksplisit ke `anon` dan `authenticated`. Mencabut salah satunya saja menyisakan yang lain — kesalahan ini terjadi dua kali secara bergantian sebelum tertutup di `029`.

7. **Fungsi `SECURITY DEFINER` mempercayai parameter identitas dari client.** `check_profile_completeness` menerima `p_user_id` apa adanya, sehingga setelah celah `anon` ditutup pun, sesama user yang sudah login masih bisa saling mengintip kelengkapan profil. Diperbaiki di `030`: identitas kini diambil dari `auth.uid()` dan parameter yang menunjuk user lain ditolak.

**Yang sengaja dibiarkan:** EXECUTE `core.is_authenticated()` dari `PUBLIC` tidak dicabut — fungsi itu dievaluasi di dalam policy RLS memakai hak role pemanggil, sehingga mencabutnya melumpuhkan RLS di seluruh database tanpa imbalan keamanan apa pun. Lima ekstensi di schema `public` (`vector`, `pg_trgm`, `btree_gist`, `btree_gin`, `moddatetime`) juga dibiarkan karena memindahkannya berisiko memecah index dan tipe kolom yang memakainya.

**Pelajaran yang dicatat permanen di `AGENTS.md`:** isi repository bukan cermin isi database. Policy RLS untuk seluruh schema domain ternyata ada di database tapi tidak ada di `017_rls.sql` — kesimpulan soal keadaan database tidak boleh diambil hanya dari membaca file migration.

**Pola yang sama ketemu lagi 2x, kali ini bukan di `authenticated`+`customer` (`027`), tapi di kombinasi role/schema lain:**

8. **`service_role` tidak pernah diberi `GRANT USAGE` ke schema domain manapun** (`customer`, `core`, `chat`, `property`, `auth_ext`) — cuma otomatis dapat di `public`. Ketemu saat verifikasi runtime `POST /api/leads/intake` di production: `permission denied for schema customer`. `service_role` punya atribut `BYPASSRLS`, tapi itu cuma melewati evaluasi RLS policy, bukan GRANT dasar. Diperbaiki **cuma untuk schema `customer`** di `032` (scope sengaja dipersempit ke yang benar-benar dipakai hari ini).

9. **`authenticated` tidak pernah diberi GRANT ke `chat.conversations`/`chat.messages`.** Policy RLS `authenticated_all` sudah benar, tapi widget "Recent Chats" di dashboard selalu balas `Error: Unable to load conversations` karena GRANT dasarnya tidak ada. Diperbaiki di `034`.

**Audit menyeluruh dilakukan setelah temuan ke-2 ini** (23 September 2026) untuk memetakan celah yang tersisa, supaya sesi berikutnya tidak perlu menemukan ulang satu-satu. Hasilnya:

| Role | Schema tanpa `USAGE` |
|------|----------------------|
| `service_role` | `auth_ext`, `chat`, `core`, `property` (customer sudah diperbaiki di `032`) |
| `authenticated` / `anon` | Tidak ada — `USAGE` sudah ada di semua schema domain |

`USAGE` di level schema saja tidak cukup — perlu dicek juga per tabel. Tabel yang `authenticated` **belum** punya `SELECT`-nya (per 23 September 2026, sebelum ada kebutuhan nyata jadi sengaja belum diperbaiki):

- `core.audit_logs`, `core.permissions`, `core.role_permissions`, `core.roles`, `core.settings`
- `property.categories`, `property.listings`

**Implikasi untuk kerja berikutnya:** kalau mulai membangun modul yang menyentuh RBAC (`core.roles`/`permissions`) atau Property Module (`property.listings`), **cek dulu** `has_table_privilege(role, 'schema.table', 'SELECT')` sebelum menulis kode query-nya — jangan asumsikan GRANT otomatis ada hanya karena RLS policy-nya ada. `getPropertySummary.ts` saat ini murni stub (return angka 0 hardcode, parameter `supabase`-nya bahkan tidak dipakai) — bukan diblokir GRANT, memang belum pernah diimplementasikan.

**Catatan operasional:** perintah `GRANT` lewat Supabase MCP (`execute_sql`/`apply_migration`) **selalu ditahan otomatis** oleh classifier permission Claude Code ("Permission Grant"), butuh konfirmasi eksplisit dari Yohan di chat tiap kali — bukan sekali setting lalu selesai. Ini kejadian konsisten sepanjang sesi 23 September (migration `032` dan `034` sama-sama sempat tertahan dulu).

**10. `authenticated_all` di `customer.leads` berarti "semua akun yang login lihat SEMUA data" — bukan cuma milik sendiri.** Baru disadari 23 September 2026 (malam) saat Yohan sadar masih pakai `admin@yohanai.id` padahal ada akun kedua di sistem: `ramlan.hadiansyah@gmail.com` (rekan Yohan di Griya Indonesia, daftar 27 Agustus 2026 lewat Google OAuth, sebelum platform lock aktif). Dengan policy lama, akun itu otomatis bisa melihat semua 1968 lead. Diperbaiki di `035`:
   - Kolom baru `customer.leads.assigned_to` (kepemilikan CRM).
   - 1968 lead lama di-assign ke `admin@yohanai.id` (disepakati sebagai data milik bisnis/owner).
   - Ramlan diberi role `agent` (dari `core.roles`, sudah ada sejak awal tapi baru dipakai sekarang).
   - Fungsi `core.is_admin_or_above()` + policy baru `leads_owner_or_admin`: admin/super_admin lihat semua, role lain cuma lihat lead yang `assigned_to` dirinya.
   - Diverifikasi lewat simulasi JWT langsung di database (bukan cuma baca kode): admin lihat 1968, Ramlan lihat 0, Ramlan bisa insert lead miliknya sendiri, Ramlan ditolak insert lead atas nama admin.

**Keputusan yang masih ditunda (disengaja, bukan lupa):** `admin@yohanai.id` untuk sementara tetap dipakai Yohan sehari-hari (develop/testing dengan data asli) sekaligus berperan admin. Pemisahan akun developer murni vs akun bisnis Yohan yang sesungguhnya ditunda sampai strukturnya "firm" — jangan buru-buru memisahkan ini di sesi berikutnya tanpa dikonfirmasi ulang dulu.

# Platform Lock

Diaktifkan 23 September 2026 saat project masuk hold.

**Cara kerja:** gate di `src/lib/platform-lock.ts`, dipanggil dari `src/proxy.ts` lewat `updateSession()`. Default-nya **terkunci** — platform hanya terbuka kalau env var `PLATFORM_LOCKED` di-set eksplisit ke `false`, supaya deploy tanpa env var tidak diam-diam membuka pendaftaran publik lagi.

| Env var | Fungsi |
|---------|--------|
| `PLATFORM_LOCKED` | Sumber kebenaran, dibaca middleware. `false` = platform terbuka |
| `NEXT_PUBLIC_PLATFORM_LOCKED` | Flag UI saja (menyembunyikan link ke route mati). Set berbarengan |
| `PLATFORM_ALLOWED_EMAILS` | Daftar email yang boleh masuk selama terkunci, dipisah koma. Kosong = semua akun terdaftar boleh |

**Route yang tetap terbuka selama terkunci:** `/under-development`, `/login`, `/forgot-password`, `/reset-password`, `/callback` (OAuth Google harus bisa mendarat), `/privacy-policy` & `/data-deletion` (URL-nya terdaftar di Google OAuth consent screen), `/api/health`.

**Route yang diblokir total:** `/register` dan `/verify-email` — diblokir di proxy sekaligus di `page.tsx`-nya sebagai lapis kedua.

**Bug yang ketemu saat memasang lock — `middleware.ts` tidak pernah jalan.** File-nya ada di root project, padahal project ini memakai direktori `src/` sehingga Next mencarinya di `src/` (sejajar dengan `app/`). Next mengabaikannya tanpa peringatan apa pun. Terbukti dari dev log: `GET /` balas `200` bukan redirect, dan `/dashboard` juga `200` — yang membelokkan ke login selama ini cuma `AuthGuard` di sisi client. Artinya refresh sesi Supabase lewat middleware tidak pernah aktif sejak awal. Diperbaiki sekaligus ke konvensi Next 16: file dipindah ke `src/proxy.ts` dengan named export `proxy` (Next 16 mendeprecate nama `middleware` menjadi `proxy`; runtime-nya `nodejs`, bukan `edge`). Setelah pindah, gate terverifikasi jalan di dev.

**Penguncian di level Supabase:** toggle *Allow new users to sign up* di Supabase Authentication dimatikan. Ini yang benar-benar mengunci — blokir di aplikasi saja tidak cukup, karena `anon key` ada di bundle browser dan endpoint signup Supabase bisa dipanggil langsung tanpa lewat UI.

**Cara membuka kembali:** set `PLATFORM_LOCKED=false` + `NEXT_PUBLIC_PLATFORM_LOCKED=false` di Vercel, lalu nyalakan lagi toggle signup di Supabase. Tidak ada kode yang perlu diubah — landing page lama, halaman register, dan semua form-nya masih utuh di codebase.
