# Database Schema

Yohan.AI memakai PostgreSQL 17 di Supabase dengan **schema terpisah per domain**, bukan satu schema `public` berisi semua tabel. Setiap tabel selalu dirujuk lengkap dengan nama schema-nya, misalnya `customer.leads`, bukan `leads`.

---

# Schema yang Digunakan

| Schema | Isi |
|--------|-----|
| `auth_ext` | Perluasan data user di luar `auth.users` bawaan Supabase |
| `core` | Tabel sistem: role, permission, setting, audit |
| `customer` | Lead dan kontak — inti modul CRM |
| `property` | Katalog dan listing properti |
| `chat` | Percakapan dan pesan |
| `ai` | Model, prompt, dan hasil interaksi AI |
| `workflow` | Definisi dan eksekusi otomasi |
| `marketing` | Campaign dan template |
| `knowledge` | Basis pengetahuan untuk AI |
| `reporting` | Dashboard dan metrik |

## Exposed Schemas

Supabase hanya mengekspos `public` dan `graphql_public` ke Data API secara default. Schema `auth_ext`, `core`, `customer`, `chat`, dan `property` sudah ditambahkan manual di **Settings → Data API**. Schema yang belum ter-expose tidak akan bisa diakses dari aplikasi sama sekali, sekalipun RLS dan GRANT-nya sudah benar.

# Tabel per Schema

## auth_ext

### profiles

Profil pengguna: nama, kontak, alamat, `business_role_id`, tautan media sosial, dan `role_details` JSONB. Terhubung satu-satu ke `auth.users`.

### notification_preferences

Preferensi notifikasi per user, satu baris per user. Empat kategori toggle; kategori Keamanan Akun sengaja tidak punya toggle dan selalu aktif.

## core

### roles, permissions, role_permissions

Role-based access control.

### business_roles

Peran bisnis pengguna di industri properti, dipakai Edit Profile untuk menentukan field wajib.

### settings

Konfigurasi sistem.

### audit_logs

Jejak aktivitas sistem.

## customer

### leads

Tabel inti CRM. Berisi identitas calon pembeli, `lead_source_id`, kolom `metadata` JSONB bebas isi, serta `status` dengan pipeline tetap:

```
new → contacted → qualified → proposal → negotiation → won → lost
```

### lead_sources

Asal lead. Sudah terisi: Facebook, Instagram, TikTok, WhatsApp, Website, Referral, Google Ads, Organic Search.

### contacts

Riwayat kontak per lead.

## property

### categories, listings

Kategori dan listing properti.

## chat

### conversations, messages

Percakapan dan pesan per lead.

## ai

### models, prompts, interactions

Konfigurasi model AI, prompt, dan riwayat interaksi.

## Tabel referensi wilayah

`wilayah_provinsi`, `wilayah_kabupaten`, `wilayah_kecamatan`, dan `wilayah_desa` — dataset wilayah administratif Indonesia berkode Kemendagri. Terisi 38 provinsi, 514 kabupaten/kota, 7.285 kecamatan, dan 83.762 desa/kelurahan, tervalidasi silang dengan angka resmi tanpa baris yatim. Dipakai cascading selector di Edit Profile, di-query per level — bukan diambil sekaligus.

### profile_completeness_rules

Aturan kelengkapan profil yang bersifat table-driven: field wajib dibaca dari tabel ini, bukan di-hardcode di form. Mendukung field kondisional lewat `depends_on_field_key`.

# Konvensi Tabel

Hampir seluruh tabel memakai pola yang sama:

- Primary key `UUID` dengan `gen_random_uuid()`
- `created_at`, `updated_at`, `deleted_at` — penghapusan bersifat soft delete
- `created_by`, `updated_by` merujuk `auth.users(id)`
- Trigger `core.update_updated_at_column()` untuk menjaga `updated_at`
- `ENABLE ROW LEVEL SECURITY` pada semua tabel

# RLS dan GRANT adalah Dua Lapisan Berbeda

Ini sumber kesalahan yang sudah dua kali memakan waktu di project ini.

**Policy RLS yang benar tidak cukup.** Role `authenticated` juga harus diberi `GRANT SELECT/UPDATE` pada tabelnya. Tanpa grant dasar itu, query akan gagal walaupun policy RLS-nya sudah tepat.

**Kondisi nyata per 23 September 2026, diverifikasi langsung ke database:**

Seluruh tabel domain (`customer`, `property`, `chat`, `ai`, `workflow`, `marketing`, `knowledge`, `reporting`) **sudah punya** policy `authenticated_all` berbasis `core.is_authenticated()`. Policy ini ada di database tapi tidak ada di `017_rls.sql` — jadi ini pun termasuk perubahan yang dijalankan di luar migration.

Ketiga tabel `customer.*` sempat **tidak punya GRANT sama sekali** untuk role `authenticated` — policy benar, grant dasarnya tidak pernah diberikan, sehingga query dari aplikasi ditolak Postgres sebelum RLS sempat dievaluasi. Diperbaiki di `027_fix_missing_grants.sql`: `leads` dan `contacts` kini SELECT/INSERT/UPDATE/DELETE, `lead_sources` SELECT saja.

**RLS aktif tanpa policy sama sekali berarti semua akses ditolak.** `public.profile_completeness_rules` sempat berada dalam kondisi ini, sehingga query langsung dari client di `EditProfileForm.tsx` selalu mengembalikan nol baris — daftar field wajib diam-diam kosong, sementara progress bar tetap tampak benar karena dihitung RPC `SECURITY DEFINER` yang menembus RLS. Policy SELECT-nya ditambahkan di `025_profile_completeness.sql`.

Tulis `GRANT` eksplisit dan `DROP POLICY IF EXISTS` di setiap migration sejak awal supaya idempotent.

# Riwayat Migration

Folder `supabase/migrations/` berisi `001`–`027` secara berurutan, dan riwayat itu **cocok persis dengan yang tercatat di database** (diverifikasi lewat `supabase migration list`, 23 September 2026).

| Rentang | Isi |
|---------|-----|
| `001`–`021` | Skema dasar, RLS awal, seed, storage, dan validasi pasca-deployment |
| `022`–`026` | Objek Sprint 011: `core.business_roles`, empat tabel wilayah, perluasan `auth_ext.profiles`, `profile_completeness_rules` beserta RPC-nya, dan `auth_ext.notification_preferences` |
| `027` | Perbaikan GRANT `customer.*` dan pencabutan hak tulis berlebih di schema `public` |

Migration `022`–`026` adalah **rekonstruksi**: objeknya sudah lebih dulu ada di database sejak Agustus 2026 karena dijalankan langsung lewat Supabase SQL Editor tanpa pernah tercatat sebagai migration. Pada 23 September 2026 seluruhnya ditarik ulang dari struktur database hidup, ditulis idempotent, lalu diterapkan — sehingga repository kembali bisa dipakai membangun database dari nol.

**Tabel wilayah adalah pengecualian.** Migration `023` hanya membuat strukturnya. Isinya — 83.762 baris desa dan seterusnya — diimport terpisah lewat CSV dari dataset berkode Kemendagri, terlalu besar untuk ditaruh sebagai `INSERT` di dalam migration. Membangun database dari nol berarti menjalankan import itu sebagai langkah tersendiri.
