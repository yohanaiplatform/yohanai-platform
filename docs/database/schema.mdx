# Database Schema

Yohan.AI memakai PostgreSQL 17 di Supabase dengan **schema terpisah per domain**, bukan satu schema `public` berisi semua tabel. Setiap tabel selalu dirujuk lengkap dengan nama schema-nya, misalnya `customer.leads`, bukan `leads`.

---

# Schema yang Digunakan

| Schema | Isi |
|--------|-----|
| `auth_ext` | Perluasan data user di luar `auth.users` bawaan Supabase |
| `core` | Tabel sistem: role, permission, setting, audit |
| `customer` | Lead dan kontak — inti modul CRM |
| `property` | Katalog dan listing properti |
| `chat` | Percakapan dan pesan |
| `ai` | Model, prompt, dan hasil interaksi AI |
| `workflow` | Definisi dan eksekusi otomasi |
| `marketing` | Campaign dan template |
| `knowledge` | Basis pengetahuan untuk AI |
| `reporting` | Dashboard dan metrik |

## Exposed Schemas

Supabase hanya mengekspos `public` dan `graphql_public` ke Data API secara default. Schema `auth_ext`, `core`, `customer`, `chat`, `property`, `ai`, dan `knowledge` sudah ditambahkan manual di **Settings → Data API** (9 dari ~14 schema non-Postgres-internal; `ai` dan `knowledge` dikonfirmasi ulang ter-expose 1 Oktober 2026 lewat probe REST langsung, bukan cuma asumsi). Schema yang belum ter-expose tidak akan bisa diakses dari aplikasi sama sekali, sekalipun RLS dan GRANT-nya sudah benar.

**Schema `marketing`, `reporting`, `workflow` -- sisa skema aspirasional pra-Claude, sengaja dibiarkan tidak di-expose.** Diverifikasi 1 Oktober 2026: dibuat lewat migration `002_schemas.sql` (bagian skema dasar awal, sebelum era Claude Code), berisi tabel kosong (`marketing.campaigns`/`.templates`, `reporting.dashboards`/`.metrics`, `workflow.executions`/`.steps` -- 0 baris semua) kecuali `workflow.definitions` yang punya **1 baris placeholder** ("Lead Qualification", `definition: {}` kosong, `created_at` 15 Juli 2026 -- jauh sebelum migrasi Claude Code dimulai). **Tidak direferensikan kode apa pun di `src/`** (dicek lewat grep menyeluruh). Konsisten dengan `project-docs/` (arsip era ChatGPT/Qwen) yang memang menyebut visi modul Marketing/Reporting/Workflow otomatis sebagai rencana jangka panjang -- schema-nya sudah disiapkan di database tapi belum pernah ada fitur yang dibangun di atasnya. **Aman diabaikan** sampai ada permintaan eksplisit untuk membangun salah satu modul itu.

# Tabel per Schema

## auth_ext

### profiles

Profil pengguna: nama, kontak, alamat, `business_role_id`, tautan media sosial, `brand_name` (migration `053`), dan `role_details` JSONB. Terhubung satu-satu ke `auth.users`. Kolom `notification_whatsapp_number` (migration `059`, 2 Oktober 2026) -- nomor WA pribadi untuk terima ringkasan notifikasi follow-up AI Agent, SENGAJA terpisah dari nomor WA bisnis di `chat.whatsapp_numbers` yang dipakai AI Agent balas lead.

### notification_preferences

Preferensi notifikasi per user, satu baris per user. Empat kategori toggle; kategori Keamanan Akun sengaja tidak punya toggle dan selalu aktif. Kolom `daily_report_email` (migration `045`, default `true`) — toggle kelima, kontrol kirim/tidaknya Daily Report ke email login user.

### google_contacts_connections

Koneksi OAuth Google Contacts **per user** (migration `047`, 29 September 2026). `user_id` (PK, `REFERENCES auth.users`), `refresh_token`, `google_email`. RLS own-row-only — tiap user cuma bisa lihat/hapus koneksinya sendiri. Diisi lewat `/api/google-contacts/callback` setelah user sambungkan akun Google pribadinya di halaman Settings; dipakai `POST /api/leads/[id]/sync-contact` untuk auto-create kontak saat lead manual (`/crm/new`) dibuat.

### google_contacts_access_requests

Permintaan akses jadi test user Google OAuth (migration `048`, 29 September 2026 malam) — Google mewajibkan penambahan manual per email selama consent screen mode "Testing", tidak bisa diotomasi dari sisi app. `user_id` (PK), `status` (`pending`/`approved`), `resolved_at`, `resolved_by`. User insert baris `pending` sendiri (RLS own-row), admin update jadi `approved` lewat RLS `core.is_admin_or_above()` (bukan service_role) setelah menambahkan manual di Google Cloud Console. Dipakai alur "Ajukan Akses" di Settings + notifikasi in-app ke admin (lihat `core.notifications`) + bagian "Permintaan Akses Tertunda" di Platform Report.

## core

### roles, permissions, role_permissions

Role-based access control. `role_permissions` masih 0 baris — keputusan admin/bukan-admin sementara cukup biner lewat `core.is_admin_or_above()`, belum pakai permission granular.

### Fungsi SECURITY DEFINER

- `is_authenticated()` — dipanggil dari policy RLS seluruh tabel domain. **Jangan pernah cabut EXECUTE-nya** — melumpuhkan RLS di seluruh database.
- `is_admin_or_above()` (`035`) — true kalau pemanggil (`auth.uid()`) admin/super_admin. Dipakai policy `leads_owner_or_admin`.
- `list_assignable_users()` (`036`) — daftar user (id, nama, email, role) untuk dropdown assign lead. Return **kosong** (bukan raise exception) kalau pemanggil bukan admin/super_admin — UI CRM pakai ini buat auto-hide dropdown assign untuk non-admin.
- `get_platform_stats()` (`046`) — ukuran database & storage Supabase (bytes, jumlah objek storage), dipakai Platform Report. EXECUTE cuma untuk `service_role` (dipanggil dari cron `GET /api/reports/daily`, bukan dari browser).

### notifications

Notifikasi in-app generik (migration `048`, 29 September 2026 malam) — pertama kali dipakai project ini, sebelumnya `NotificationMenu.tsx` (bell icon) cuma dummy 2 item hardcode. `recipient_id`, `type`, `title`, `body`, `link`, `metadata` JSONB, `read_at`. **INSERT sengaja TIDAK di-grant ke `authenticated`** — menulis notifikasi untuk user lain (mis. broadcast ke semua admin) harus lewat `createAdminClient()` di route handler (`src/lib/notifications/createNotification.ts`), bukan langsung dari sesi user biasa. `authenticated` cuma boleh SELECT/UPDATE baris miliknya sendiri (tandai `read_at`). Dipakai pertama kali untuk notifikasi permintaan akses Google Contacts (`type: 'google_contacts_access_request'`/`'google_contacts_access_approved'`).

### business_roles

Peran bisnis pengguna di industri properti, dipakai Edit Profile untuk menentukan field wajib.

### settings

Konfigurasi sistem.

### audit_logs

Jejak aktivitas sistem.

## customer

### leads

Tabel inti CRM. Berisi identitas calon pembeli, `lead_source_id`, `assigned_to` (kepemilikan CRM — lihat bagian akses di bawah), kolom `slug` (unik, dipakai URL `/crm/<slug>`, dibuat otomatis dari nama saat insert — migration `055`, pola identik `property.listings.slug` tapi dengan backfill collision-safe lewat window function karena sudah ada ribuan lead existing; TIDAK diregenerasi kalau nama lead diedit lagi), kolom `metadata` JSONB bebas isi, serta `status` dengan pipeline tetap:

```
new → contacted → qualified → proposal → negotiation → won → lost
```

**"Temperature" (Hot/Warm/Cold/Closing/Batal) BUKAN kolom `status`.** Untuk lead dari Google Form legacy, itu ada di `metadata->>status_funnel_awal`. Dua konsep berbeda — jangan disamakan.

### lead_sources

Asal lead. Sudah terisi: Facebook, Instagram, TikTok, WhatsApp, Website, Referral, Google Ads, Organic Search, **Google Form** (ditambahkan 23 September 2026, migration `031`), **Input Manual** (ditambahkan 26 September 2026, migration `037`, dipakai form `/crm/new`).

### contacts

Riwayat kontak per lead. Skema ada, belum dipakai kode aplikasi manapun.

### lead_temperature_history

**Nyata, dipakai** (migration `063`, 4 Oktober 2026). Riwayat perubahan Temperature lead (`metadata->>status_funnel_awal`) -- sebelumnya hanya ditimpa tanpa jejak. Diisi OTOMATIS oleh trigger `trg_log_lead_temperature_change` (AFTER INSERT/UPDATE OF metadata di `customer.leads`, fungsi SECURITY DEFINER `customer.log_lead_temperature_change()`, EXECUTE dicabut dari PUBLIC/anon/authenticated) dari jalur APA PUN (UI, AI Agent, SQL). Kolom: `from_temperature`, `to_temperature`, `source` (`manual` kalau `auth.uid()` ada, `otomatis` kalau service_role/AI), `changed_by_user`, `created_at`. RLS: SELECT admin atau agent yang `assigned_to` lead itu; tulis hanya lewat trigger/service_role. Belum ada backfill (riwayat mulai 4 Okt 2026). Dasar analisis pola funnel (Data Analysis Agent).

### notes

Catatan per lead, **append-only** (migration `038`, 26 September 2026) — cuma `SELECT`+`INSERT` di-GRANT ke `authenticated` (tidak ada UPDATE/DELETE dari app lewat sesi login). Kolom `author_label` disimpan mentah saat insert (snapshot nama penulis saat itu), bukan di-resolve dari `auth_ext.profiles` saat ditampilkan — RLS profil cuma izinkan baca punya sendiri, jadi non-admin yang lihat note tulisan admin di lead miliknya tidak bisa resolve nama itu lewat query biasa. RLS `notes_owner_or_admin` ikut visibilitas lead induknya (via `EXISTS` ke `customer.leads`), pola sama seperti `leads_owner_or_admin`. **`service_role` dapat GRANT `SELECT`+`INSERT`+`UPDATE` terpisah di migration `054`** (1 Oktober 2026 malam) — dipakai AI Agent (`applyAgentDecision.ts`) untuk menyimpan/update "ringkasan percakapan otomatis" per lead (`author_label = "AI Agent (ringkasan otomatis)"`): note lama di-soft-delete (`deleted_at`) lalu insert baru, bukan UPDATE isi note (tetap konsisten dengan prinsip append-only), jadi cuma 1 ringkasan yang aktif per lead.

## property

### categories, listings

Kategori (9 baris, mis. Rumah/Tanah/Ruko; soft delete lewat `deleted_at`, dikelola dari `/properties/categories`) dan listing properti. `listings` punya kolom `slug` (unik, dipakai URL `/properties/<slug>`, dibuat otomatis dari judul saat insert — lihat `src/lib/property/slugify.ts`) dan `assigned_to` (kepemilikan per agent, sama pola seperti `customer.leads.assigned_to` — lihat bagian akses di bawah) selain `id`. Field spesifikasi (kamar tidur/mandi, luas tanah/bangunan, carport, sertifikat, status, video_url, contact_phone, photo_urls) semua di kolom `metadata` JSONB, pola sama seperti `customer.leads` — bukan kolom tersendiri.

**Akses `listings` dibatasi per agent** (migration `043`, pola identik `leads_owner_or_admin` di `035`): policy `listings_owner_or_admin` — admin/super_admin lihat semua, role lain cuma lihat `assigned_to = auth.uid()`. Reuse `core.is_admin_or_above()` dan `core.list_assignable_users()` yang sudah ada, tidak ada fungsi baru. `categories` tetap `authenticated_all` (dikonfirmasi eksplisit ke Yohan — kategori bukan data sensitif per-agent).

# Konvensi Tabel

Hampir seluruh tabel memakai pola yang sama:

- Primary key `UUID` dengan `gen_random_uuid()`
- `created_at`, `updated_at`, `deleted_at` — penghapusan bersifat soft delete
- `created_by`, `updated_by` merujuk `auth.users(id)`
- Trigger `core.update_updated_at_column()` untuk menjaga `updated_at`
- `ENABLE ROW LEVEL SECURITY` pada semua tabel

# RLS dan GRANT adalah Dua Lapisan Berbeda

Ini sumber kesalahan yang sudah berkali-kali memakan waktu di project ini — di kombinasi role/schema yang berbeda-beda tiap kali.

**Policy RLS yang benar tidak cukup.** Role apa pun (`authenticated`, `service_role`, dll) juga harus diberi `GRANT USAGE` ke schema dan `GRANT SELECT/INSERT/UPDATE` ke tabelnya. `BYPASSRLS` yang dipunya `service_role` cuma melewati evaluasi RLS policy, bukan pengganti GRANT dasar. Tanpa grant, query gagal duluan di level Postgres sebelum RLS sempat relevan.

**Kondisi nyata per 23 September 2026, diverifikasi langsung ke database:**

Seluruh tabel domain (`customer`, `property`, `chat`, `ai`, `workflow`, `marketing`, `knowledge`, `reporting`) **sudah punya** policy berbasis `core.is_authenticated()`. Beberapa policy ini ada di database tapi tidak ada di `017_rls.sql` — jadi ini pun termasuk perubahan yang dijalankan di luar migration.

**Empat kejadian GRANT hilang, ditemukan terpisah:**

1. `authenticated` × `customer.leads`/`contacts` — diperbaiki `027`.
2. `service_role` × schema `customer` — `service_role` cuma otomatis dapat `USAGE` di `public`, sama sekali tidak di schema domain manapun. Diperbaiki **cuma untuk `customer`** di `032` (belum untuk `auth_ext`/`chat`/`core`/`property` — sengaja ditunda sampai ada kode yang butuh).
3. `authenticated` × `chat.conversations`/`chat.messages` — diperbaiki `034`.
4. `service_role` × schema `chat` — dibutuhkan begitu webhook WhatsApp (`POST /api/whatsapp/webhook`) mulai ditulis dan dipanggil pakai `createAdminClient()`. Diperbaiki `039`.
5. `authenticated` × schema `property` (schema **dan** tabel `categories`/`listings`) — 0 akses sama sekali sebelum Property Module mulai dibangun. Diperbaiki `041`.
6. Beberapa tabel `core.*` (RBAC: `roles`, `permissions`, `role_permissions`, `settings`, `audit_logs`) masih belum punya GRANT `authenticated` sama sekali per hari ini — **cek dulu** `has_table_privilege()` sebelum membangun fitur yang menyentuhnya.
7. `service_role` × `auth_ext`/`core` (`profiles`, `notification_preferences`, `roles`) — dibutuhkan begitu Daily Report (`GET /api/reports/daily`, jalan pakai service-role key dari cron) mulai ditulis, untuk resolve daftar penerima laporan + cek toggle `daily_report_email`. Diperbaiki `045`. `service_role` masih belum punya `USAGE` di `chat`/`property` (belum ada kode yang butuh dari jalur service-role).

**RLS aktif tanpa policy sama sekali berarti semua akses ditolak.** `public.profile_completeness_rules` sempat berada dalam kondisi ini, sehingga query langsung dari client di `EditProfileForm.tsx` selalu mengembalikan nol baris — daftar field wajib diam-diam kosong, sementara progress bar tetap tampak benar karena dihitung RPC `SECURITY DEFINER` yang menembus RLS. Policy SELECT-nya ditambahkan di `025_profile_completeness.sql`.

**Policy `USING true` (semua-yang-login-lihat-semua) itu sendiri bisa jadi bug kalau tabelnya dipakai lebih dari satu akun.** `customer.leads` pakai policy seperti ini sejak awal — begitu ada akun kedua terdaftar (bukan cuma Yohan), akun itu otomatis kebagian akses penuh ke seluruh data lead, tanpa direncanakan siapa pun. Diganti di `035` jadi policy `leads_owner_or_admin`: kolom `assigned_to` + fungsi `core.is_admin_or_above()` — role admin/super_admin lihat semua, role lain cuma lihat lead miliknya sendiri. **Jangan default ke policy semacam ini untuk tabel data sensitif per-user/per-agen.**

Tulis `GRANT` eksplisit dan `DROP POLICY IF EXISTS` di setiap migration sejak awal supaya idempotent. Verifikasi policy scoped paling akurat lewat simulasi JWT langsung (`SET LOCAL request.jwt.claims = '{"sub":"<uuid>"}'`), bukan cuma baca definisi policy-nya.
