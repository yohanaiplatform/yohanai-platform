# Skema Data

**Tabel:** `property.categories` (id, name, description) dan `property.listings` (id, **slug** (unik, migration `042`), category_id, **assigned_to** (kepemilikan per agent, migration `043`), title, description, address, price, **metadata JSONB**, timestamps). Tidak ada tabel `property.images` terpisah — semua field tambahan (spesifikasi + foto) disimpan di kolom `metadata`, mengikuti pola yang sama seperti `customer.leads` (bukan kolom per-field). `slug` sendiri kolom asli (unik, NOT NULL), bukan di metadata, karena dipakai routing URL — dibuat otomatis dari judul saat insert (`src/lib/property/slugify.ts`), ditambah suffix `-2`/`-3` dst kalau ada tabrakan judul.

```json
{
  "status": "available" | "booked" | "sold" | "hold",
  "bedrooms": number | null,
  "bathrooms": number | null,
  "land_area": number | null,
  "building_area": number | null,
  "carport": number | null,
  "certificate_type": "SHM" | "HGB" | "Girik" | "Lainnya" | null,
  "video_url": string | null,
  "contact_phone": string | null,
  "photo_urls": string[],
  "ai_tags": string[],
  "hidden": boolean,
  "owner": { "name": string | null, "phone": string | null } | null,
  "commission": { "type": "percentage" | "fixed" | null, "value": number | null } | null
}
```

`photo_urls[0]` = foto sampul, dipakai di grid list & (rencananya) flyer promosi.

**`owner`/`commission` (28 September 2026) — rahasia, admin + agent yang di-assign saja.** Tidak perlu migration/RLS baru: policy `listings_owner_or_admin` (`043`) yang sudah ada kebetulan pas persis dengan kebutuhan ini — kalau sebuah listing kelihatan sama sekali oleh seorang user, user itu pasti admin atau agent yang di-assign (satu-satunya audiens yang disetujui Yohan lihat data ini), jadi RLS row-level yang sudah ada otomatis cukup. Yang perlu dibatasi tambahan cuma EDIT-nya (admin-only) — dilakukan di level UI (`PropertyConfidentialFields.tsx`), pola sama seperti dropdown "Ditugaskan ke" (`PropertyAssignSelect.tsx`): deteksi admin lewat `core.list_assignable_users()` (array kosong = bukan admin). **Field ini sengaja TIDAK PERNAH dikirim** ke `PropertyExportButtons`/`exportFlyer.ts` atau path publik apa pun — kalau nanti ada halaman listing publik (buat SEO/crawler), `metadata.owner`/`metadata.commission` wajib di-strip eksplisit sebelum dikirim ke client, jangan spread `metadata` mentah.

**GRANT:** `authenticated` sebelumnya **0 akses** ke schema `property` (temuan audit 23 September 2026, sengaja belum diperbaiki karena belum ada kode yang butuh) — diperbaiki di migration `041` begitu Property Module mulai dibangun. Storage bucket `properties` sudah ada dari migration `019` (public), tidak perlu bucket baru. **`service_role` juga sempat 0 akses ke schema `property`** (pola yang sama seperti temuan `customer`/`chat` di `AGENTS.md`) — ditemukan 28 September 2026 saat skrip migrasi bulk listing (pakai `service_role` key) gagal dengan "permission denied for schema property", diperbaiki di migration `044`.

**RLS `property.categories`:** policy `authenticated_all` (`USING core.is_authenticated()`) ternyata sudah ada di database sejak awal, tapi **tidak tercatat di migration manapun** di repo — ditemukan 26 September 2026 saat verifikasi sebelum membangun halaman Kelola Kategori (pola yang sama seperti temuan audit 23 September di `AGENTS.md`: isi repo bukan cermin isi database). GRANT `authenticated`: SELECT/INSERT/UPDATE ada (`041`), **DELETE tidak ada** — bukan masalah karena hapus kategori memakai soft delete (`deleted_at`), bukan DELETE asli.

**RLS `property.listings`:** sama seperti `categories`, policy `authenticated_all` yang ada di database sebelum migration `043` juga **tidak pernah tercatat di file migration manapun** — ditemukan 27 September 2026 saat verifikasi sebelum membangun kepemilikan per agent. Diganti di `043` jadi policy `listings_owner_or_admin`, identik pola `leads_owner_or_admin` (`035`): admin/super_admin lihat semua, role lain cuma lihat `assigned_to = auth.uid()`. Reuse `core.is_admin_or_above()` dan `core.list_assignable_users()` — tidak ada fungsi baru. Diverifikasi lewat simulasi JWT langsung (bukan cuma baca policy): admin lihat listing, Ramlan (role `agent`, belum ditugaskan listing manapun) lihat 0.

## Laporan Pemasaran / Marketing Report (`/properties/[slug]/report`, 1 Oktober 2026)

✅ **Selesai.** Diminta Yohan untuk digenerate ke vendor/pemilik listing, format sama seperti laporan manual lama ("Laporan Vendor" PDF, contoh referensi: listing Kapur Mas Residence) -- sekarang otomatis dari data lead platform, bukan diisi manual.

**Tidak ada relasi FK langsung antara `customer.leads` dan `property.listings` di database** -- lead dicocokkan ke listing lewat dua jalur (digabung, bukan saling eksklusif):

1. **`metadata->>kategori` lead cocok ke `metadata.lead_kategori_match` listing** (array kategori, dikonfigurasi lewat checkbox langsung di halaman laporan, `ListingLeadKategoriMatch.tsx`) -- cocok untuk kategori yang sudah spesifik ke satu listing (mis. "Calon Konsumen Kapur Mas" -> listing Kapur Mas).
2. **`metadata.manual_listing_id` di lead** (dropdown "Kaitkan ke Listing" di Lead Detail, `LeadListingLink.tsx`) -- override manual buat lead dengan Kategori yang terlalu umum (mis. "Kons. Cari Rumah Murah") yang tidak otomatis cocok ke listing manapun; agen tentukan sendiri berdasarkan hasil percakapan WA.

Keputusan ini diambil eksplisit dari klarifikasi Yohan (1 Oktober 2026) -- opsi lain yang dipertimbangkan (tambah kolom `listing_id` wajib di tiap lead) ditolak karena ~2000 lead lama tidak akan punya link itu.

**Isi laporan** (`getListingReport.ts`, `src/app/(dashboard)/properties/[slug]/report/page.tsx`):
- Header: Judul listing, alamat, **Dilaporkan Kepada** (`metadata.owner.name`/`.phone`, field yang sama seperti "Data Pemilik & Komisi"), periode laporan (filter tanggal, default 30 hari terakhir). **Nama brand di kanan atas header diambil dari `auth_ext.profiles.brand_name` agen yang generate laporan** (field baru "Nama Brand" di Edit Profile, 1 Oktober 2026 sore, lihat bawah) -- fallback ke nama lengkap agen kalau kosong. **Sengaja TIDAK hardcode "Griya Indonesia Real Estate"** seperti versi awal -- lihat memory `multi-tenant-forward-compat`, platform ini akan dipakai bisnis lain juga. Website yang tertera masih statis `yohanai.id` untuk semua user (belum ada fitur landing page per-user).
- **Data Prospek** -- tabel lead yang cocok di periode itu, **dibatasi ke 10 lead TERBARU saja** (`DISPLAY_LEAD_LIMIT` di `getListingReport.ts`) supaya laporan muat 1 halaman cetak -- diminta eksplisit Yohan setelah cek hasil nyata (laporan contoh sempat 2 halaman). Kolom: Nama, Keterangan (`komentar`/`permintaan`/`minat_unit_lokasi`, fallback berurutan, **dipotong ke 60 karakter** `truncateKeterangan()` supaya baris tabel tidak melebar ke bawah), **Telepon disamarkan 6 digit terakhir** (`maskPhone()`, mis. `+6281234••••••` -- laporan ini keluar ke vendor/pemilik eksternal, bukan dipakai internal), Agent (resolve nama dari `auth_ext.profiles`), Tanggal Input. Catatan "Menampilkan X dari Y lead paling baru" muncul kalau totalnya lebih dari 10.
- **Sumber Informasi** -- breakdown + persentase per kategori `sumber_informasi` yang SUDAH ada di CRM sekarang (Iklan Meta/Google, Ketemu di Lokasi, dst) -- **bukan** kategori di laporan lama (Spanduk/Website/Media Sosial/dst, sumber sistem lama yang berbeda total), keputusan eksplisit Yohan supaya datanya akurat tanpa kerja tambahan. **Dihitung dari SEMUA lead yang cocok di periode itu, bukan cuma 10 yang ditampilkan di tabel** -- supaya statistiknya tetap akurat walau tabelnya dipotong.
- **Catatan Agent** dan **Rekomendasi** -- teks bebas, diisi agen sebelum export, **tidak disimpan ke database** (sekali pakai per laporan, sama seperti form kertas lama). Textarea-nya **auto-resize mengikuti isi** (`useAutoResizeTextarea` di `PropertyMarketingReportControls.tsx`, ukur `scrollHeight` lewat `useEffect` tiap kali teks berubah) -- bug ditemukan Yohan sendiri: textarea biasa (`rows` tetap) nyimpen scrollbar internal yang ikut kebawa ke hasil cetak/PDF karena `window.print()` cuma merender DOM apa adanya, bukan nge-scroll ke tiap bagian, jadi teks panjang kepotong di hasil cetak. **Kalau catatannya panjang sampai laporan jadi lebih dari 1 halaman A4, itu memang diterima** (dikonfirmasi Yohan) -- yang tidak boleh cuma teks tersembunyi di balik scroll.
- **Tidak ada bagian "Aktifitas"** (Pembicaraan Telepon/Kunjungan Pribadi/dst dari laporan lama) -- platform belum punya data ini sama sekali (bukan fitur yang sudah ada), sengaja di-skip di v1 per keputusan Yohan, bukan terlewat.

**Export: `window.print()` browser, BUKAN html2canvas+jsPDF** (beda dari `PropertyFlyer.tsx`) -- laporan ini tabel/teks panjang yang butuh auto-pagination multi-halaman, cuma disediakan print engine browser, bukan canvas tunggal. CSS `@media print` di `globals.css` (class `.print-area`/`.no-print`) sembunyikan semua chrome aplikasi saat print, tampilkan cuma badan laporan.

**Bug ditemukan & diperbaiki saat testing manual**: query awal lead-per-listing cuma 1 request tanpa pagination -- PostgREST membatasi 1000 baris per request secara default, jadi listing dengan lead sangat banyak (mis. Kapur Mas, >1300 lead) diam-diam terpotong ke 1000 tanpa peringatan. Ketemu karena laporan sempat nampilkan persis "1000 lead" -- angka bulat yang mencurigakan. Diperbaiki dengan loop `.range()` (pola sama seperti `getAllLeadsForExport()` di CRM) -- diverifikasi ulang cocok persis lewat `COUNT(*)` SQL langsung (1325 = 1325).

**"Nama Brand" per user (1 Oktober 2026 sore, `auth_ext.profiles.brand_name`, migration `053`)** -- field baru TEXT, opsional, kolom polos (bukan JSONB) karena berlaku sama untuk semua business role, bukan per-role seperti `role_details`. **Sengaja TIDAK dimasukkan ke `profile_completeness_rules`** -- bukan syarat kelengkapan profil, murni identitas tambahan buat laporan. Ditambahkan di `EditProfileForm.tsx` bagian "Lengkapi Profil" (Tier 2 umum), state hardcode sama seperti `avatarUrl`/`facebookUrl` (bukan driven dari `profile_completeness_rules`, field-field general section itu memang selalu hardcode, beda dari "Detail Tambahan" per-role yang data-driven). **Ini bagian KECIL dari permintaan lebih besar Yohan yang sengaja DITUNDA**: redesain halaman Profile (sembunyikan field yang tak perlu tampil ke user, tambah logo + setting watermark) -- lihat memory `profile-page-redesign-deferred`.

## Watermark Foto (28 September 2026)

Setiap foto yang diupload lewat `uploadListingPhoto.ts` (baik dari form Tambah Listing maupun halaman Detail) otomatis dikasih watermark logo Yohan.AI di tengah, sebelum diupload ke Storage. Implementasi murni **Canvas API bawaan browser** (`src/lib/property/watermarkPhoto.ts`) -- tidak nambah dependency npm apa pun. Pakai `logo-dark.png` (versi teks putih, dipakai header saat dark mode) dengan opacity 55% + shadow hitam, supaya tetap kebaca di foto terang maupun gelap -- **bukan** `app-icon.png` yang dipakai boot/loading screen. Kalau logo gagal dimuat atau canvas tidak didukung, foto tetap diupload tanpa watermark daripada gagal total.

**Watermark retroaktif ke foto lama** -- Yohan minta semua foto yang sudah terupload sebelum fitur ini ada (91 hasil migrasi spreadsheet + beberapa listing manual, total **291 foto**) juga dikasih watermark. Karena file-file itu ada di Storage (bukan di browser lagi), dipakai `sharp` (server-side, `npm install sharp`) lewat skrip Node.js satu-kali (tidak disimpan di repo), bukan `watermarkPhoto.ts` yang berbasis Canvas browser. **Bug sempat ketemu saat development skrip ini**: percobaan pertama pakai "plakat" latar gelap di belakang logo (meniru shadow versi Canvas) menghasilkan watermark yang pecah/tidak sejajar -- setelah diselidiki, penyebabnya BUKAN plakat-nya, tapi skrip sempat dijalankan 2x ke foto tes yang sama sehingga watermark bertumpuk. Disederhanakan jadi cuma logo + opacity (tanpa plakat/shadow tambahan), diverifikasi bersih di foto yang belum pernah disentuh sebelum dijalankan ke semua 291 foto. **Hasil akhir: 291/291 berhasil, 0 gagal** (diverifikasi lagi dengan spot-check acak setelah batch selesai).

## Migrasi dari Spreadsheet (28 September 2026)

**91 listing** dari spreadsheet legacy Griya Indonesia ("Listing Baru 2024 Terbaru", sheet "Input Data") dimigrasikan ke `property.listings` lewat skrip Node.js satu-kali (tidak disimpan di repo -- one-off, bukan reusable, dijalankan lokal pakai `SUPABASE_SERVICE_ROLE_KEY`). Hasil: **91/91 listing masuk, 285/285 foto berhasil diunduh ulang dari Google Drive dan diupload ke Storage bucket `properties`** (jauh lebih baik dari ekspektasi -- log AutoCrat lama di spreadsheet sempat mencatat 55/91 link foto rusak, ternyata sebagian besar sudah bisa diakses lagi sekarang).

**Keputusan yang diambil sebelum migrasi (dikonfirmasi eksplisit ke Yohan):**
- **Kepemilikan (`assigned_to`):** semua 91 listing di-assign ke admin dulu (bukan dipetakan ke 9 agen berbeda di data lama, cuma 2 yang punya akun platform sekarang -- Yohan & Ramlan).
- **`contact_phone`:** diseragamkan ke nomor kantor Griya Indonesia (`0821-5041-5012`), bukan nomor pribadi pemilik properti yang ada di data lama.
- **Data pribadi pemilik** (KTP, tanggal lahir, pekerjaan, alamat, No. HP pemilik) -- **sengaja tidak diimpor sama sekali**, tidak ada tempat/fitur untuk itu di schema sekarang.
- **Foto:** dicoba migrasikan yang linknya masih valid (bukan skip) -- hasilnya 100% berhasil dari yang dicoba.

**Masalah data yang ditemukan & ditangani saat migrasi:**
- **Bug parsing harga:** 1 listing ("Tanah Ruko Tepi Jalan Pak Benceng Pontianak") sempat salah jadi `Rp 16` karena harga aslinya ditulis teks "1.6 M per kapling" (bukan format angka standar) -- parser digit-only salah menafsirkannya. Diperbaiki manual jadi `Rp 1.600.000.000` setelah ditemukan lewat pengecekan visual di `/properties`, bukan cuma percaya laporan "0 gagal" dari skrip migrasi.
- **Luas tanah/bangunan ambigu** (7 nilai, mis. "36, 45, 60" untuk kompleks multi-tipe, "65+") -- sengaja dikosongkan sebagai angka, teks aslinya tetap masuk deskripsi supaya tidak ada data yang salah tebak.
- **Listing kemungkinan duplikat:** ditemukan 9 kelompok (20 listing) dengan pemilik+harga identik tapi judul/baris berbeda di spreadsheet asli (kemungkinan disubmit ulang via Google Form) -- **sengaja tidak dihapus otomatis**, karena sebagian bisa jadi memang listing berbeda dalam satu kompleks. Perlu ditinjau manual oleh Yohan.
- Kolom pipeline `customer.leads.status`-style yang serupa tidak ada masalah di sini karena `property.listings` tidak punya kolom pipeline seperti itu -- field `status` (available/booked/sold/hold) di metadata semuanya di-default `"available"`, belum ada sumber data yang bisa dipercaya untuk status sebenarnya (data spreadsheet dari 2024, sebagian mungkin sudah terjual).
