Baris uji sudah dihapus lagi dari database.

Sempat ketemu bug tambahan saat verifikasi ini: `service_role` ternyata belum pernah diberi `GRANT USAGE` ke schema `customer` (baru ketahuan sekarang karena baru sekarang ada fitur pertama yang pakai service-role key) — endpoint sempat balas `permission denied for schema customer`. Diperbaiki di migration `032_grant_service_role_customer_schema.sql`. Detail pola masalahnya sudah dicatat di `AGENTS.md` bagian jebakan.

**Status per 23 September 2026, malam:** kurir Apps Script (`YohanAI_LeadIntake.gs`) sudah ditempel Yohan, trigger "On form submit" sudah terpasang (trigger tambahan, tidak mengubah/menghapus 8 trigger legacy yang sudah ada), kolom `Synced At` & `YohanAI Lead ID` sudah ditambahkan di sheet "Input Data". Backfill `backfillLeadsToYohanAI()` sudah/sedang dijalankan Yohan berkali-kali (dibatasi ~6 menit per run oleh Apps Script, jadi wajar butuh beberapa kali klik Run) — total lead di spreadsheet ±1968, per pengecekan terakhir di database sudah masuk 1141+ dan terus bertambah.

**Kalau mulai sesi baru dan mau tahu progres backfill saat ini**, cek langsung:

```sql
select count(*) from customer.leads where metadata->>'origin' = 'google_form_legacy';
```

Bandingkan dengan total di spreadsheet (kartu "Total" di dashboard Apps Script lama). Kalau sudah sama-sama ~1968, backfill selesai — jalankan ulang query di migration `033` sekali lagi (idempotent, aman diulang) untuk membenahi `created_at` baris-baris yang masuk di jeda waktu sebelum perbaikan `route.ts` ter-deploy:

```sql
UPDATE customer.leads
SET created_at = (regexp_replace(metadata->>'submitted_at', ' GMT.*$', '')::timestamp AT TIME ZONE 'Asia/Jakarta')
WHERE metadata->>'origin' = 'google_form_legacy'
  AND metadata->>'submitted_at' ~ '^[A-Za-z]{3} [A-Za-z]{3} \d{2} \d{4} \d{2}:\d{2}:\d{2} GMT'
  AND created_at::date = now()::date;
```

(Filter `created_at::date = now()::date` sengaja dibatasi ke baris yang masih "hari ini" — supaya tidak menyentuh baris yang sudah benar.)

## Sync Google Contacts — personal per user (✅ Selesai, 29 September 2026)

### Lanjutan diskusi (27-28 September 2026) — dua model dipetakan, belum dipilih

Dibahas ulang lebih dalam saat ngobrol soal AI Agent (lihat `docs/modules/ai.mdx`). Dipetakan 2 model berbeda, penting dipisahkan karena implikasinya beda total:

**Model A — SaaS multi-tenant sungguhan.** Satu deployment (satu Vercel + satu Supabase project) melayani banyak bisnis sekaligus, data terisolasi per tenant lewat kolom `tenant_id`/`organization_id` di semua tabel domain + RLS ditulis ulang total (termasuk `leads_owner_or_admin` dan `listings_owner_or_admin` yang baru dibangun — keduanya baru scoped per-agent dalam SATU tenant, belum lintas tenant). **Model B — Duplikasi instance per pelanggan.** Deploy ulang seluruh stack (Supabase project baru + Vercel project baru + akun Kapso/nomor WA baru) untuk tiap bisnis baru, bukan satu platform dipakai bareng. **Nol perubahan kode** — murni kerjaan operasional (jalankan migration yang sama di database baru). Tiap instance berdiri sendiri penuh.

**Rekomendasi (belum final, nunggu ada permintaan konkret):** mulai dari Model B kalau/ketika ada pelanggan pertama, jangan re-arsitektur Model A tanpa demand nyata.

**Soal kepemilikan akun infrastruktur (relevan untuk Model B):** Supabase & Vercel sebaiknya dipusatkan di akun Yohan sendiri — pelanggan baru tidak pernah login ke situ (pola "managed hosting", sama seperti Ramlan sekarang tidak punya akses Supabase sama sekali, cuma login ke produk jadi). Kapso beda ceritanya karena WhatsApp mewajibkan verifikasi bisnis asli per nomor — nomor & identitas bisnis pelanggan baru harus tetap atas nama mereka sendiri, bukan atas nama Yohan.

### Struktur Tim & Role (1 Oktober 2026) — visi, BELUM dibangun

Yohan mau platform ini mendukung dua mode kerja sekaligus (bukan pilih salah satu): **tim** (agent freelance/kantor broker yang biasa kerja dalam grup di bawah satu leader) dan **solo** (agent yang mau kerja sendiri, fokus maksimalkan fitur AI Agent untuk dirinya). Detail lengkap di memory `multi-tenant-team-hierarchy`, ringkasannya:

- **Hierarki SENGAJA cuma 1 layer referral**, bukan berjenjang bebas: seseorang daftar `manager` → merekrut beberapa `agent` jadi timnya. Agent TIDAK BOLEH recruit sub-agent lagi.
- **Upgrade agent → manager**: kalau agent (mis. "D") mau punya tim sendiri, dia naik role jadi `manager` (kriteria/upgrade berbayar, mekanisme belum diputuskan) — begitu naik, dia **terputus dari tim lama** (bukan agent dari manager sebelumnya lagi) dan mulai rekrut tim baru dari nol, TAPI tetap bawa lead/listing yang sudah assigned ke dirinya sendiri sebagai modal awal. Satu orang tidak bisa jadi agent di satu tim sekaligus manager di tim lain.
- **"Admin" di level manager bukan role ke-4 terpisah** — role `manager` otomatis punya hak semacam admin tapi DI-SCOPE ke timnya sendiri saja (dirinya + agent yang dia rekrut), tidak bisa lihat tim manager lain, tidak platform-wide. Beda total dari Master Admin (`admin@yohanai.id`/`super_admin`) yang lihat semua tim semua tenant.
- **Agent solo bukan role baru** — cuma `agent` tanpa afiliasi tim (tidak ada manager). Kebutuhan "maksimalkan AI Agent untuk pribadi" itu urusan paket/tier berlangganan (mis. "Individual Pro" vs "Team"), bukan urusan RBAC role — dua sumbu berbeda (role = siapa lihat data siapa, tier = fitur apa yang didapat).
- **Implikasi desain kalau Model A dipilih**: hierarki 1-layer ini jauh lebih sederhana untuk RLS dibanding org-chart berjenjang bebas — cukup cek "manager_id milik lead/listing ini == aku?" (satu hop), tidak perlu recursive query. Kemungkinan kolom `manager_id` nullable di `auth_ext.profiles` (bukan tabel `teams` terpisah dulu, karena cuma 1 layer), null berarti solo/independent atau Master Admin.
- Masih tahap visi/dicatat — jangan mulai bangun skema ini sebelum Model A/B benar-benar diputuskan.

**Riset Kapso (28 September 2026):** dicek langsung ke `docs.kapso.ai` dan `kapso.com/platform` — Kapso ternyata sudah punya fitur persis untuk ini, disebut **"Multi-partner Solution"**, di tier **Platform ($299/bulan)**: satu akun Kapso bisa pegang sampai **50 nomor WA terhubung** (tambahan di atas itu $5/nomor), tiap tenant menyelesaikan verifikasi WhatsApp Business-nya sendiri (Meta embedded signup, tetap atas nama bisnis mereka) lewat link setup yang dikirim dari akun Kapso pusat, lalu webhook mengonfirmasi begitu nomor itu tersambung — semua tenant terlihat dari satu dashboard (kesehatan, pesan, usage, billing). Tidak tersedia di Free/Pro (Free cuma 1 nomor, Pro cuma 3). **Kesimpulan: sisi Kapso/WhatsApp BUKAN penghalang untuk Model A** kalau nanti dipilih — penghalang aslinya tetap murni skema database/RLS, belum berubah dari kesimpulan 26 September.

## Prinsip: jangan buang Google Form-nya

Google Form sudah bekerja dan calon lead sudah terbiasa memakainya. Membangun ulang form di dalam platform berarti mengambil risiko tanpa mendapat apa pun — form tetaplah form.

Yang berubah bukan form-nya, melainkan **ke mana datanya pergi**. Sekarang: Form → Spreadsheet, dan spreadsheet itu sumber kebenaran. Nanti: Form → Spreadsheet **dan** → YohanAI, dengan database sebagai sumber kebenaran dan spreadsheet turun pangkat jadi cadangan.
